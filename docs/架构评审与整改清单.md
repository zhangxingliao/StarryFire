# StarryFire 架构评审与整改清单

> 来源：全量代码走读（HAL / SYS / GUI / 两个 App / 板级配置 / 文档）评审。
> 本文档合并评审结论 + 整改行动清单 + 执行记录，后续**按优先级逐条整改，一条完成后经确认再启动下一条**。
> 与 `docs/评审记录与待拍板清单.md`（H/M/L/N 清单）互引，已在对应条目标注，避免重复劳动。

---

## 0. 总体结论

架构方向正确、工程化程度高于同类 ESP32 GUI 框架：编译期 Kconfig 裁剪 + Android 式 App 生命周期 + BSP 板级包，三者选型与 ESP32-S3 资源模型匹配，属于该量级项目的合理解。分层、命名、线程模型（单 GUI Task）基本自洽。

但存在 3 个结构性问题需要正视，且代码与 DESIGN.md 之间存在一批「文档声称已实现、代码其实只做了一半」的偏差。

- 架构整体评级：**B+**（方向对、裁剪理念出色，但存在双向耦合与事件线程模型隐患）
- 代码-框架一致性评级：**B−**（核心机制兑现，但接口表/主题/板级抽象存在「声明了未做满」的半成品状态）

---

## 1. 做对的事（亮点）

1. **板级抽象方案是最大亮点**：`boards/<name>/` 组件 + `SF_BOARD` 探测 + `SDKCONFIG_DEFAULTS` 合并 + `EXTRA_COMPONENT_EXCLUDE_DIRS` 排他，让「换板只改 boards/」真正落地，多板冲突防护考虑周全。
2. **单 GUI Task + esp_lvgl_port 锁**：LVGL 访问面收口正确（sf_hal_core.c 栈提至 16KB 也正确）。
3. **状态机表驱动生命周期**：`sf_app_manager.c` 合法转移表 + 非法转移拦截告警，优于散落 if/else。
4. **Monitor App data/UI 解耦**：`sf_monitor_*_data.c` 各自持有「快照 + 互斥锁 + collect/log」，UI 层不碰 FreeRTOS，接口契约清晰。

---

## 2. 结构性风险

### R1. GUI ↔ System 运行期双向依赖环
- **现象**：编译期 include 图是 `sf_gui → sf_sys`（单向），但运行期是环：
  - AppManager 持有 GUI 注入的 UI hooks（`sf_app_manager_set_ui_hooks`，sf_app_manager.c:55-69）并反向调用 GUI 逻辑；
  - GUI 又回调 `sf_app_pause_current` / `sf_app_start`（sf_gui_phone_shell.c:67、sf_gui_launcher.c:22）。
- **定性**：不是错误（嵌入式窗口管理普遍如此），但架构文档应如实描述——AppManager 实际是「持有窗口管理回调的调度器」。
- **整改（P1）**：将 `sf_app_manager_set_ui_hooks` 声明从 sf_sys.h 挪到明确标记「由 GUI 层注入」的接口区；DESIGN.md §4.2 补充运行期协作描述，避免误导后续维护者。

### R2. 事件分发跨三种上下文，subscriber 回调在发布者上下文中同步执行
- **现象**：事件流横跨 esp_event task（bridge 转发）→ GUI task（订阅回调）→ 业务逻辑。
  - `sf_settings_wifi.c` 的 `wifi_event_cb` 在 esp_event task 里直接 `lvgl_port_lock` + 刷 UI（当前行 520-542），会阻塞整个事件循环，并与 GUI task 存在锁竞争——即 H4 数据竞争的架构根源。
  - 通知链路 bridge → on_event → `sf_notification_post` → publish → on_notification_event 全程在 esp_event task 里同步穿行（sf_notification.c:34-56），任何一环阻塞都会拖垮 Wi-Fi 事件。
- **整改（P0）**：订阅回调一律只做「置脏/发通知」，UI 刷新统一由 GUI 侧定时器聚合。`sf_gui_notification_center.c` 用 `lv_async_call` 是正确做法，`sf_settings_wifi.c` 直接刷 UI 是反例。

### R3. 返回栈（history）逻辑缺陷
- **评审原描述**（基于旧版代码）：`sf_app_start` 无条件 `push_history`，而 `sf_app_go_back` pop 后调 `sf_app_start` 又 push 回去，导致返回失效。
- **现状核实（2026-08-11 会话）**：**主体已修复**（会话前期 P0#1 落地）。当前：
  - `resume_foreground`（sf_app_manager.c:312-347）与 history 解耦；
  - `sf_app_start`（:349-366）仅在公开启动路径 push（push_history 相邻去重）；
  - `sf_app_go_back`（:397-420）走独立 pop-and-resume 路径，**不再调用 sf_app_start**，不会重推入栈。
  - 推演 A→B→C 后连续 go_back：B→A→（栈底）无操作，均正确；eviction 场景（history 引用已 DESTROYED→UNREGISTERED 的 slot）也能经 resume_foreground 重建恢复。
- **状态**：已修复，复核通过。剩余收尾可选：补充 go_back 场景回归推演用例。

- `sf_` 前缀、`CONFIG_SF_*` 配置宏、`esp_err_t` 错误码——命名规范一致。
- 生命周期 7 状态 + UI hooks 驱动 ui_root 创建/销毁，与文档一致。
- 事件桥接（WIFI/IP → EventBus）、主题运行时切换 + 持久化、`SF_UI()` 缩放——均落地。
